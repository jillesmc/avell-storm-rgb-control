# ADR-002: Implicit "last applied look" instead of explicit save or profiles

## Status

Accepted (user decision, 2026-10-06)

## Date

2026-10-06

## Context

The user asked that "once I saved some animation or state I want, whenever the app opens that state must be applied".

There were three ways to define "saved":
- automatically keep the last applied look;
- an explicit "Save as startup" action;
- named profiles with one marked as the startup look.

In the GUI, firmware effects and solid colours already apply automatically (200 ms debounce). Per-key and palette slots apply with **Apply**. The user prefers few controls and steps (ADHD-friendly docs and UI were requested earlier).

## Decision

The **last look whose USB apply succeeded** becomes the device's saved look, automatically, with no save button.
- Follow-screen, demo test pattern and freeze never change it.
- Named profiles are deferred to a follow-up spec.

## Alternatives Considered

### Alternative 1: Explicit "Save as startup" button

- **Description**: Experiment freely; only an explicit save changes the startup look.
- **Pros**: Experiments never overwrite the preferred look.
- **Cons**: One more step to remember. Easy to forget, which leads to "it didn't come back" surprises.
- **Why rejected**: The user chose automatic.

### Alternative 2: Named profiles

- **Description**: Several saved looks, one marked as startup.
- **Pros**: Most powerful.
- **Cons**: Much larger scope (management UI, CLI, storage).
- **Why rejected**: Out of scope now; it can build on the same state file later.

## Consequences

### Positive

- Zero extra steps: the app reopens as the user left it.
- It reuses the existing apply points, so each one only needs to emit a persist update.

### Negative

- Experimenting overwrites the previous look; there is no "undo to my favourite".

### Risks

- A failed or partial apply must never overwrite the saved look. Enforced by save-on-success (spec BR-4, Safety Invariant 2).

## Implementation Notes

- Backends emit `persistUpdate` from inside the USB task after the driver call returns. The facade writes on the GUI thread.
