# ADR-001: Saved device state in a Qt-free JSON file

## Status

Proposed

## Date

2026-10-06

## Context

The feature must persist, per device kind:
- the remembered USB id;
- the light state;
- the last applied look (firmware effect, solid colour, per-key grid, animation reference, LED bar parameters).

Today the GUI persists only two booleans, through `QSettings` (`ui/closeToTray`, `ui/autoConnectOnStartup`), in `~/.config/avell-storm-rgb/Avell Storm RGB.conf`.

The user also decided that the CLI must **show** and **restore** the saved state without the GUI (`avell-storm-rgb state show|restore`). The CLI package (`avell_storm_rgb`) does not depend on PySide6; `pyusb` is its only runtime dependency.

The data is a small nested document, with discriminated look variants and up to 126 per-key cells.

## Decision

Store the state in **one JSON document**, `${XDG_CONFIG_HOME:-~/.config}/avell-storm-rgb/state.json`:
- schema `version: 1`;
- owned by a new **Qt-free** module, `avell_storm_rgb.application.device_state` (model, validation, atomic save, quarantine, restore functions);
- the GUI is the only writer; the CLI only reads.

`QSettings` keeps UI preferences only (`ui/closeToTray`).

## Alternatives Considered

### Alternative 1: QSettings keys

- **Description**: Store each field as a `QSettings` key (`devices/keyboard/look/mode`, …).
- **Pros**: Matches the current settings mechanism; no new file.
- **Cons**: The CLI would need PySide6 to read it, or would have to parse Qt's INI quoting by hand. Nested variants and arrays are awkward. There is no schema version.
- **Why rejected**: It breaks the decision that the CLI restores without the GUI, and it couples the core to Qt.

### Alternative 2: SQLite

- **Description**: A small database in the config dir.
- **Pros**: Transactions, room to grow (profiles).
- **Cons**: Overkill for one small document. Harder to inspect by hand or by an agent. Needs migration tooling.
- **Why rejected**: No querying need. Named profiles are a non-goal for now.

### Alternative 3: One JSON file per device

- **Description**: `keyboard.json`, `led_bar.json`.
- **Pros**: Smaller writes.
- **Cons**: Two files to keep consistent (migration, quarantine); no gain at this size.
- **Why rejected**: More moving parts for no benefit.

## Consequences

### Positive

- The CLI and agents can read the state with `state show --json` or by reading the file.
- The core owns the model and restore logic, so the GUI and CLI behave the same.
- Atomic replace protects against partial writes.

### Negative

- Settings live in two places (`QSettings` for UI preferences, `state.json` for devices).
- Strict validation means one bad field invalidates the whole file (mitigated by quarantine and an error message).

### Risks

- Manual edits while the GUI runs are overwritten. Documented in `_dx.md`.
- A future schema change needs a version bump and a migration path. `version` is checked from day one.

## Implementation Notes

- Atomic write: temp file in the same directory, flush + `os.fsync`, then `os.replace`. Directory mode `0700`, file mode `0600`.
- Unknown `version` or a schema violation → `StateFileError`. The GUI quarantines the file to `state.json.invalid`; the CLI exits 3.
- The legacy `ui/autoConnectOnStartup` is migrated once, then deleted (spec BR-14).
