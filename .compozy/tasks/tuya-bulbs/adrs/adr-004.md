# ADR-004: One shared screen capture

## Status

Accepted (user decisions Q8, Q9 — 2026-11-01; capture sharing stated in Q9 and confirmed in the summary)

## Date

2026-11-01

## Context

Follow sources are selectable per bulb: Keyboard, Screen, LED bar (Q8). Today follow-screen runs entirely inside a keyboard USB task: capture plus `set_key_colors` in one loop on the USB thread (`keyboard_backend.py:1357-1370`, `screen_follow_wayland.py:24-90`). On Wayland, each capture opens the portal window picker. A bulb following the screen while the keyboard does not would need a capture with no keyboard task; two captures would mean two pickers and twice the work.

## Decision

1. Split capture from apply: `iter_screen_frames(stop, **region)` yields RGB frames (X11 or Wayland), and the existing keyboard apply stays in `screen_follow_frame.py`.
2. `ScreenFrameHub` (GUI, own thread) owns the only capture. Subscribers are ref-counted: the first starts it (one picker), the last stops it.
3. The keyboard becomes a subscriber. Each frame is coalesced (latest wins) into one `UsbWorker` task that writes the 16×6 map. Follow-screen therefore no longer occupies the USB thread, which resolves debt #6 for follow-screen.
4. Bulbs subscribe and use the frame's average colour.
5. The CLI `keyboard follow-screen` keeps its behaviour through a thin loop over `iter_screen_frames`.

## Alternatives Considered

### Alternative 1: A second capture for bulbs

- **Description**: bulbs run their own capture loop.
- **Pros**: no change to the keyboard path.
- **Cons**: two portal pickers on Wayland; double CPU.
- **Why rejected**: contradicts the confirmed "one capture" design.

### Alternative 2: Screen source only via the keyboard

- **Description**: the Screen option works only while the keyboard follows the screen.
- **Pros**: trivial.
- **Cons**: the bulb cannot follow the screen on its own; a confusing dependency.
- **Why rejected**: the user chose an independent Screen source (Q8).

## Consequences

### Positive

- One picker, one capture. LED bar commands no longer wait behind follow-screen.

### Negative

- Touches a working feature (follow-screen) on both X11 and Wayland.

### Risks

- Regression in follow-screen timing or stop behaviour. Mitigation: characterisation tests on the keyboard writes before the refactor, the stop event preserved per subscriber, and a manual X11 + Wayland check.

## Implementation Notes

- The hub emits `frame` (queued) with a downscaled image. The keyboard sink keeps `enable_user_mode()` on its first frame.
- Capture interval stays 0.1 s; consumers coalesce.
