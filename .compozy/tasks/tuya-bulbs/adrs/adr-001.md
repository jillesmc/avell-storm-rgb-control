# ADR-001: tinytuya extra, imported keys, private inventory file

## Status

Accepted (user decisions Q2, Q3, Q4 — 2026-11-01)

## Date

2026-11-01

## Context

Tuya bulbs are controlled on the LAN with a per-device local key that only the Tuya cloud hands out. The user already has a working setup in `~/git/iot`: tinytuya 1.20, a `devices.json` from `python -m tinytuya wizard`, and the cloud credentials in `tinytuya.json`. The app must stay usable with no bulbs, and must not add a mandatory dependency (repo rule: no new dependency without a request; extras for optional features).

## Decision

1. Add an optional extra `tuya = ["tinytuya>=1.20,<2"]`. Only `src/avell_storm_rgb/infrastructure/tuya/` imports it, lazily.
2. Onboarding is **import only**: the app reads the wizard's `devices.json` (GUI button, `bulb import`). No cloud account in the app.
3. Keys live in a separate inventory file `tuya_devices.json`, mode 0600, written atomically. `state.json` never contains keys.

## Alternatives Considered

### Alternative 1: Own implementation of protocol 3.3

- **Description**: AES-ECB + CRC framing (~200 lines) on top of `cryptography`.
- **Pros**: no new package.
- **Cons**: only 3.3; we would own a protocol that tinytuya already maintains (3.1–3.5).
- **Why rejected**: user chose the extra (Q2).

### Alternative 2: Tuya cloud account in Settings

- **Description**: API key/secret/region stored in the app; fetch devices and keys on demand.
- **Pros**: no terminal step; refresh keys after re-pairing.
- **Cons**: a stored cloud secret; the IoT Core trial expires and must be renewed.
- **Why rejected**: user chose import (Q3); can be a later spec.

### Alternative 3: Keyring (KWallet / Secret Service)

- **Description**: store keys with `keyring`.
- **Pros**: encrypted at rest.
- **Cons**: one more dependency; fails while the wallet is locked at login, exactly when the autostart runs.
- **Why rejected**: user chose a 0600 file (Q4).

## Consequences

### Positive

- Zero impact without the extra; the same code path as the user's working script.
- `state.json` stays safe to paste in an issue.

### Negative

- Re-pairing a bulb requires re-running the wizard and re-importing.
- Keys are plain text, protected only by file permissions.

### Risks

- tinytuya API drift (e.g. `set_colour` turning bulbs on) → pin `<2`, write DPS directly where semantics matter (ADR-002), adapter tests against a stub.

## Implementation Notes

- `uv add --optional tuya "tinytuya>=1.20,<2"`.
- `os.open(tmp, O_WRONLY|O_CREAT|O_TRUNC, 0o600)` + `os.replace`.
- All inventory writes (import, remove, `set_last_ip`) take an advisory `flock` on `<inventory>.lock`, re-read and then replace. Without it, a worker's `set_last_ip` can overwrite a concurrent CLI import.
- Right after the lazy `tinytuya` import, pin `logging.getLogger("tinytuya")` to WARNING. Never call `tinytuya.set_debug()`: it runs `logging.basicConfig(level=DEBUG)` and tinytuya logs the local key in clear (`core/XenonDevice.py:1085`).
- Import keeps `id`, `name`, `key`, `mac`, `version`→`protocol`, `ip`→`last_ip` when present; only category `dj`.
