# ADR-003: Bulb network I/O model

## Status

Accepted (user decision Q11 — 2026-11-01)

## Date

2026-11-01

## Context

GUI USB I/O runs on one thread (`UsbWorker`). Long tasks there already block other devices (debt #6). Bulb commands are network calls: 0.2–1.2 s with a fresh connection, 20–130 ms on a persistent one (measured on the three bulbs). Tuya devices usually accept a single local TCP client, and the user may run `bulbs.py` or another LAN client.

## Decision

1. `BulbWorker`: one single-thread executor per bulb id. Commands for one bulb run in order; bulbs never wait on each other; nothing runs on the GUI or USB thread.
2. Connections are opened per command and closed afterwards, except while that bulb follows a source. Then one persistent socket stays open, colour pushes use `nowait`, and a status read runs every 5 s.
3. While that socket is open it is the **only** driver for the bulb: every user command and every follow push for that bulb runs on the same executor and through it. `close()` runs on follow→none, disconnect, forget, remove, unavailable and shutdown. Opening a second driver for a following bulb is a bug.
4. Follow pushes are coalesced on the GUI thread: a 250 ms tick per following bulb sends only the latest colour, only if it changed by at least 8 in some channel, and only if no push for that bulb is still in flight.
5. Bulb operations never use the busy overlay.

## Alternatives Considered

### Alternative 1: Always-persistent connections

- **Description**: one socket per remembered bulb with heartbeats and pushed updates.
- **Pros**: instant state updates; fast commands.
- **Cons**: locks out other local clients for as long as the app runs (all day, via autostart).
- **Why rejected**: user chose on-demand (Q11).

### Alternative 2: Reuse `UsbWorker`

- **Description**: submit bulb calls to the USB queue.
- **Pros**: no new worker.
- **Cons**: a 5 s bulb timeout would freeze the keyboard; animations would block bulbs.
- **Why rejected**: couples unrelated devices; worsens debt #6.

## Consequences

### Positive

- An offline bulb never delays the keyboard, the LED bar or another bulb.
- Other LAN clients keep working unless a bulb is following.

### Negative

- Each command pays the connection cost (≤ 1.2 s). Outside changes appear within 30 s, not instantly.

### Risks

- Up to 3 extra threads; negligible.

## Implementation Notes

- A per-bulb `BulbSession` owns the lazily created `ThreadPoolExecutor(max_workers=1, thread_name_prefix=f"bulb-{id[-4:]}")` and at most one driver; `set_hold_open` decides whether the driver survives a task. `shutdown()` on app quit closes every session and executor.
- Signals: `opDone(bulb_id, result)` is queued to the GUI thread and is the only path to the row cache; `opFailed(text)` matches the `UsbWorker` error shape. Messages come from a `log_bulb_failure(name, exc)` helper that never formats payloads.
