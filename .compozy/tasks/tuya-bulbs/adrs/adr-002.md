# ADR-002: Bulbs are read, not restored

## Status

Accepted (user decisions Q5, Q10 — 2026-11-01)

## Date

2026-11-01

## Context

The keyboard and LED bar cannot report their colours, so the app saves the last look and re-applies it at start (remembered-devices spec). Bulbs are different: their status reports power, mode, brightness, temperature and colour, and they keep their state across power cycles. They are also house lights in other rooms, and the app starts at login.

## Decision

1. The bulb is the source of truth. The app saves no bulb look; it shows the last status read or command result.
2. Startup, retry and refresh only read (`status()`). No command is sent unless the user acts, or a follow source changes while the bulb is on.
3. Following (slice 2) never writes the power DP (20) and never sends while the last known power is off. tinytuya's `set_colour`/`set_white` add `switch: True`, so the follow path writes DPS 21/24 directly.
4. Explicit user commands (brightness, white, colour) do switch the bulb on, matching the Tuya app and `bulbs.py`.

## Alternatives Considered

### Alternative 1: Restore like the keyboard

- **Description**: save the last look and re-apply it at start.
- **Pros**: symmetric with USB devices.
- **Cons**: logging in would switch on the living-room light; stale data overrides changes made from the phone.
- **Why rejected**: user chose "don't touch, read the real state" (Q5).

### Alternative 2: Opt-in "restore at start" per bulb

- **Description**: restore only flagged bulbs.
- **Pros**: flexible.
- **Cons**: more UI and state for a case nobody asked for.
- **Why rejected**: not needed (Q5).

## Consequences

### Positive

- Logging in never changes a house light. The UI always tells the truth after one read.
- No look schema for bulbs in `state.json`.

### Negative

- Before the first read, the state is unknown, so the UI shows "Reading…".

### Risks

- Some firmware may switch on when DPS 24 is written while off (OQ-1). Mitigation: gate on the last power plus a 5 s read while following, and a manual hardware check with the user's go-ahead.

## Implementation Notes

- `BulbDriver.push_colour` = `set_multiple_values({"21": "colour", "24": hex}, nowait=True)`.
- tinytuya never raises for device errors: every call returns `{"Err", "Error", "Payload"}`. The adapter raises from `Err` (914 → `KeyRejected("local key or protocol rejected")`, 901/902/905/timeout → `BulbUnreachable`, anything else → `BulbError`), retries once on 914 when one discovery reports a different protocol version, and never copies `Error` or `Payload` into the message.
- `set_brightness`/`set_white` take the caller's `BulbStatus`; only `set_brightness(percent, None)` reads status first, on the same connection.
